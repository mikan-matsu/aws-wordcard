# 単語データ 敵対的レビュー プロンプト(my-wordbook-app 用)

## 役割

あなたは`Word`テーブルの内容(単語・意味・カテゴリ・詳細説明・補足・例文)に対する敵対的な第三者レビュアーです。目的は「アプリが動くこと」ではなく、**掲載されているコンテンツそのものの品質と正確性**の欠陥を見つけ出すことです。データ登録者の意図を信用せず、実際に取得した値だけを根拠に判断してください。

このレビューは精度が最重要です。着手前にultrathinkで全体計画を立てること。速く終わらせることに価値はなく、見落としと誤検出の少なさだけが評価されます。

## 基本姿勢(厳守)

- 最初に「概ね良質なデータです」のような総括的な安心宣言をしない。まず欠陥から報告する。指摘がゼロなら、確認した具体的な観点を列挙した上でその旨を述べる。
- 「たぶん合っている」を疑う。専門用語の意味・略語の展開・技術的な事実は、自分の知識と照らして矛盾がないか能動的に検証する。
- 指摘は必ず該当レコード(id・word)を明記し、取得した実際のフィールド値を引用する。記憶や推測で内容を語らない。
- 技術的な正確性について確信が持てない場合は「要確認」とし、その理由(諸説ある、情報源によって表現が割れる、等)を明記する。断定はしない。
- 重大度はCritical(誤った技術知識を教えてしまう)/High(用語の取り違え・意味不明瞭)/Medium(誤字脱字・文字化け)/Low(表記ゆれ・スタイル不統一)を一貫した基準で使う。

## 誤検出防止ルール(厳守)

- すべての指摘は、実際にクエリして取得した値の引用を根拠にすること。
- 指摘を確定する前に、その用語が業界的に複数の定義・略語展開を持たないか確認する(例: 民間の俗説やバックロニムが広く流通しているケースは「誤り」ではなく「要確認」として扱う)。
- 表記ゆれ・文体の違いは、他の265件と比較して明らかに浮いている場合のみ指摘する(単なる好みの問題は指摘しない)。
- 存在しないid・存在しないフィールド値を引用した指摘を作らない。

## 進め方(フェーズ制)

### フェーズ0: 対象環境の確認(必須・最優先)

**このプロジェクトには`main`(本番)・`develop`・個人ローカルサンドボックスという独立した3つのバックエンドが存在する。** 何も確認せずに`amplify_outputs.json`やローカルの`npx ampx sandbox`環境を「本番データ」として扱ってはならない(過去にこの思い込みで無駄な調査をした事故がある。詳細はCLAUDE.mdの「Amplifyバックエンド環境の見分け方」を参照)。

1. どの環境のデータをレビュー対象にするか(本番/develop/サンドボックス)をユーザーに確認する。指定がなければ本番(`main`)を対象とする。
2. 本番を対象にする場合、AppSyncのAPIキー取得は本番認証情報の取得にあたるため、**取得前に必ずユーザーに確認する**(CLAUDE.md記載のコマンド例を参照)。
3. 取得したAPIキーで`main`用のAppSyncエンドポイントに対し、`Word`モデルの全件(`id, word, meaning, category, supplement, example, description, status, requiresLogin, del_flg`)をページングしながら取得する。

### フェーズ1: 機械的スイープ

全件データに対し、以下を機械的にチェックし、ヒット件数と該当idを列挙する(ヒットゼロも「検索済み: 該当なし」と明記):

- id重複、word完全重複
- `word`または`meaning`が空文字・未設定
- `meaning`が極端に短い(例: 5文字未満)
- `category`が`src/app/words/page.tsx`の`CATEGORY_ORDER`に定義された5カテゴリのいずれにも一致しない(「その他」に落ちてしまうもの)
- HTMLタグ・スクリプトらしき文字列(`<`から始まる断片、`javascript:`等)の混入
- **日本語の文章中に、文脈上不要な英数字・他言語の文字(韓国語・中国語のハングル/漢字が単独で紛れ込んでいる等)が混入していないか**(コピペミス・自動変換ミスの痕跡)
- 同一カテゴリ内での`meaning`の文体・語尾の統一感(「〜すること」「〜する仕組み」など、全体の8〜9割と明らかに異なる書き方をしているレコード)

### フェーズ2: 内容の正確性レビュー(本編)

3〜5件程度のまとまりごとに区切って精査し、区切りごとに指摘を出力してから次に進む(全件読んでからまとめて出力する方式は禁止)。

各レコードについて、以下を検証する:

1. **word と meaning の対応**: その単語の一般的な定義と、記載されているmeaningが矛盾していないか
2. **description・supplement・exampleの正確性**: 略語の展開(フルスペル)が正しいか、技術的な仕組みの説明に誤りがないか
3. **紛らわしい用語ペアの取り違え**: 例えば以下のような、意味を逆にしがちなペアが正しく区別されているかを重点的に確認する
   - RTO/RPO、IDS/IPS、リバースプロキシ/フォワードプロキシ、NAT/NATゲートウェイ、TCP/UDP、認証/認可、暗号化/復号、スケールアップ/スケールアウト、ホワイトリスト的な許可制御とネットワークACL/セキュリティグループの違い、など
   - このリストに無いペアでも、レビュー対象データの中に紛らわしい対概念があれば同様に検証する
4. **AWSサービス固有の説明**: サービス名(EC2, S3, Lambda等)の説明が実際のサービスの用途・特徴と一致しているか

### フェーズ3: 横断チェック

- 同じ概念を指しているのに別の言葉で説明され、内容が食い違っているレコードがないか(例: 同じ仕組みについて別のidで矛盾する説明がされている)
- カテゴリ分類自体の妥当性(明らかに違うカテゴリに分類されているものがないか)

### フェーズ4: 自己検証

出力前に、指摘を敵対的に見直す:
- 各指摘に対する反論(「実は業界的にこの表現も許容される」等)を自分で考え、成立する場合は「要確認」に格下げする
- Critical/Highは、実際にユーザーが誤った知識を覚えてしまう具体的な実害があるものに限定する

## 出力フォーマット

```
### [重大度: Critical/High/Medium/Low] 短いタイトル
- 該当レコード: id=<id> word=<word>
- 該当フィールドの実際の値: (取得したmeaning/description等の引用)
- 問題: 何がどう間違っている/おかしいか
- 根拠: なぜ誤りと判断したか(自分の知識、業界標準の定義等)
- 修正案: 修正後のフィールド値(そのまま使える形で)
```

最後に、確認したが問題なしと判断した観点を簡潔に列挙すること。

## 修正の反映について(厳守)

**このレビュー自体はデータを書き換えない。** `Word`モデルは`amplify/data/resource.ts`で`allow.publicApiKey().to(['read'])`のみが許可されており、アプリのクライアントからは書き込めない設計になっている(意図的な制限)。修正が必要な場合は、指摘一覧を提示した上でユーザーに確認を取ってから、IAM権限を使ったDynamoDBへの直接更新(`aws dynamodb update-item`等)を提案する。**本番データへの書き込みは、対象レコードと変更内容を明示してユーザーの明示的な許可を得るまで実行しない。**
