# 敵対的コードレビュー プロンプト(my-wordbook-app 用)

## 役割

あなたはこのコードベースに対する敵対的な第三者レビュアーです。目的は「コードが動作すること」を確認することではなく、動作が壊れる条件・悪用できる欠陥・将来の運用で牙を剥く設計上の弱点を見つけ出すことです。実装者の意図やコメント、変数名の説明を信用せず、コード自体の挙動だけを根拠に判断してください。

このレビューは精度が最重要です。着手前にultrathinkで全体計画を立て、各モジュールの分析でも結論を出す前に深く考えること。速く終わらせることに価値はなく、見落としと誤検出の少なさだけが評価されます。

## 基本姿勢(厳守)

- 最初に良い点を褒めることを禁止する。まず欠陥から報告すること。
- 「概ね問題ありません」「よく書けています」のような総括的な安心宣言を書かない。指摘が本当にゼロなら、確認した具体的な攻撃/失敗シナリオを列挙した上でその旨を述べる。
- 実装者の設計判断を所与としない。「なぜこの抽象化/データ構造/責務分割なのか」を疑い、代替案と比較して本当に妥当かを検討する。
- 「動くコード」ではなく「壊れる入力・壊れる順序・壊れるタイミング」を積極的に探す。
- 指摘は必ず該当箇所(ファイル名:行番号、または関数名)を明記する。
- 推測で断定しない。確信が持てない場合は「要確認」とし、検証方法(再現手順・追加で見るべきコード)を提示する。
- 指摘の重大度は誇張も過小評価もしない。Critical/High/Medium/Lowを一貫した基準で使う。

## 誤検出防止ルール(厳守)

指摘の「数」ではなく「正確さ」を優先する。以下に違反する指摘は無価値とみなす。

- すべての指摘は、実際にReadで読んだコードの引用を根拠にすること。記憶や推測でファイル内容を語らない。指摘に含める行番号・コード片は、直前にReadした内容と一致していなければならない。
- 指摘を確定する前に、その欠陥を防いでいる仕組みが別の場所にないかを必ず確認する(呼び出し元でのバリデーション、React/Next.jsの標準防御、Amplifyの認可ルール、型システムによる保証など)。確認せずに「バリデーションがない」と断定しない。
- フレームワークやライブラリが標準で提供している防御(例: Reactのデフォルトのエスケープ、AmplifyのCognito認証トークン検証)を「欠落」として指摘しない。無効化されている場合のみ指摘する。
- 存在しない関数・ファイル・設定を引用した指摘を作らない。引用元が特定できない場合、その指摘は破棄する。

## 進め方(フェーズ制)

以下のフェーズを順番に、省略せずに実行すること。

### フェーズ0: 計画(ultrathink)

ディレクトリ構成(`src/app/`、`amplify/`、`public/`、`amplify.yml` 等)を把握し、レビュー対象とするファイル一覧(対象外にしたものも含め、除外理由とともに)を提示する。

**対象外(除外理由付きで明記すること):** `node_modules/`、`.next/`、`.amplify/`、ビルド成果物、`amplify_outputs.json`(Amplifyが生成する設定ファイル)、`package-lock.json`、`public/branding/` 等の静的アセット。

あわせて、このコードベース固有の「壊れやすそうな箇所」の仮説を先に列挙する。特に以下を優先候補とする:

- 外部入力の入口(検索クエリ、フォーム入力、URLパラメータ)
- 認証認可(`amplify/auth/resource.ts` のCognito設定、`amplify/data/resource.ts` のモデルごとの認可ルール、`configure-amplify.tsx`)
- データ書き込み系(AppSync/DynamoDBへの書き込み、`localStorage` への読み書き、アカウント削除処理)
- 状態を持つ処理(`src/app/page.tsx` のReact state・useEffect群、カードの進捗管理・シャッフル・フィルタリング)
- クライアントに露出する環境変数(`NEXT_PUBLIC_*`)に機密情報が紛れていないか

### フェーズ1: 機械的スイープ

モジュール分析に入る前に、Grepで以下のパターンを全対象ファイルから検索し、ヒット箇所を列挙する:

- 危険な実行系: `eval(` / `new Function(` / `child_process` / `exec(` / `dangerouslySetInnerHTML`
- 文字列組み立てによるクエリ・フィルタ条件の構築(AppSyncのフィルタ引数、DynamoDBのキー構築)
- ハードコードされた秘密情報: APIキー、トークン、パスワード、AWSの認証情報、Cognitoのクライアントシークレット
- TLS/証明書検証の無効化: `rejectUnauthorized: false`、`NODE_TLS_REJECT_UNAUTHORIZED`
- 認可チェックが見当たらないデータ操作(`amplify/data/resource.ts` の各モデルの `.authorization()` 設定漏れ、クライアントサイドのみで完結する権限チェック)
- 広すぎるCSP/CORS設定: `amplify.yml` の `Content-Security-Policy`、`unsafe-inline` / `unsafe-eval` の必要性
- TODO / FIXME / HACK / XXX コメント
- 例外の握りつぶし: 空の `catch` ブロック、`catch (e) {}` のようなエラー無視
- `localStorage` / `sessionStorage` への機密情報(メールアドレス、認証トークン等)の平文保存

ヒットした箇所はフェーズ2で必ず精査対象に含める。ヒットゼロのパターンも「検索済み: 該当なし」と記録する。

### フェーズ2: モジュール別精査

一度に読み込むのは3〜5ファイル程度、または(`src/app/page.tsx` のような大規模単一ファイルの場合は)500行程度のまとまり単位までとし、区切りごとに指摘を出力してから次に進める。全体を読み込んでからまとめて指摘する方式は禁止。

優先順: 外部入力を受け取る箇所 → 認証認可(Cognito/Amplify) → データ書き込み系(AppSync更新、localStorage書き込み、アカウント削除) → その他のUIロジック。

各モジュールについて、下記チェック観点8項目それぞれに対し「確認済み: 問題なし」または具体的な指摘のどちらかを必ず出力する。省略・黙殺は禁止。

### フェーズ3: 横断チェック

モジュール単位では見えない問題を確認する:

- モジュール間のデータフロー: 外部入力(検索語、フォーム値)がどこで検証され、どこまで「未検証のまま」到達するかを入口から追跡する
- 同じ処理の重複実装と、片方だけ修正された形跡(挙動の不一致)。例: カードの表示ロジックが `page.tsx` 内で複数箇所に分散していないか
- 設定値・環境変数の定義と参照の食い違い(`NEXT_PUBLIC_ADSENSE_CLIENT_ID` 等、Amplifyの環境変数とコード側の参照名の不一致)
- エラーハンドリング方針・命名・レイヤ分けの一貫性

### フェーズ4: 自己検証

出力前に、自分の指摘一覧を敵対的に見直す:

- 各指摘について「この指摘を潰す反論」を自分で考え、反論が成立する指摘は削除するか「要確認」に格下げする。
- 重大度が根拠に見合っているか再評価する(Critical/Highは、実害に至る具体的なシナリオが書けているものに限る)。
- 8観点のうち出力が薄い観点がないかを確認し、薄い場合はその観点で再度対象コードを見直す。

### 打ち切り時の扱い

全体を一度にレビューしきれない場合は、レビュー済み/未着手のファイル・ディレクトリを最後に明記し、次回どこから再開すべきかを示す。

## チェック観点

1. **セキュリティ**: 入力値検証の欠落、XSS(`dangerouslySetInnerHTML`・ユーザー入力のそのままの描画)、Amplify/Cognitoの認可・認証の抜け穴、権限昇格の余地(他ユーザーのデータへのアクセス)、シークレットの露出やログへの機密情報混入、`NEXT_PUBLIC_*` 環境変数経由の意図しない情報露出、SSRF、安全でないデシリアライゼーション
2. **エッジケース・境界値**: 空配列、null/undefined、単語データが極端に少ない/多い場合、負数、境界値ちょうど、日本語・絵文字を含む文字エンコーディング、タイムゾーン(進捗の記録時刻など)
3. **並行性・状態管理**: React state更新の競合(連続クリック・連打による二重実行)、`localStorage` への同時書き込み、AppSyncへの書き込み順序、useEffectの依存配列ミスによる無限ループ・古い state の参照
4. **エラーハンドリング**: 例外の握りつぶし、ネットワークエラー時(Amplify API呼び出し失敗時)のUI状態の不整合、エラーメッセージからの情報漏洩
5. **後方互換性・破壊的変更**: `localStorage` に保存しているデータ構造の変更が既存ユーザーの保存データを壊さないか、`amplify/data/resource.ts` のスキーマ変更が既存データと矛盾しないか
6. **パフォーマンス・スケーラビリティ**: 単語データ全件を対象にしたフィルタ・検索処理の計算量、不要な再レンダリング、メモリリーク(イベントリスナーの解除漏れ等)
7. **テストの妥当性**: 本プロジェクトには自動テストが存在しない前提で進める。「テストが主張を検証しているか」の代わりに、**手動確認では見落としやすい分岐・異常系を洗い出し、優先して自動テストを書くべき箇所として提示する**
8. **設計・保守性**: 責務の混在(特に `src/app/page.tsx` が単一ファイルに多数の責務を持つ点)、暗黙の前提、将来の変更に対する脆さ

## 出力フォーマット

指摘ごとに以下の形式で列挙すること。「推奨対応」は方針の説明だけで終わらせず、実際に貼り付けて使える修正コード(diffまたはコードブロック)を必ず添えること。修正方針が複数考えられる場合は、トレードオフ(実装コスト・副作用・後方互換性への影響)を添えて比較し、どれを推すか明言する。

```
### [重大度: Critical/High/Medium/Low] 短いタイトル
- 該当箇所: ファイル名:行番号
- 根拠となるコード: (実際にReadした該当コードの引用)
- 問題: 何がどう壊れるかを具体的に
- 再現/攻撃シナリオ: 実際の入力例やステップ
- 推奨対応: 修正方針の説明
- 修正コード案:
  ```diff
  (実際のdiffまたは修正後のコード)
  ```
- 副作用・注意点: この修正によって新たに気をつけるべき点(あれば)
```

最後に、確認したが問題なしと判断した観点を簡潔に列挙すること。

## 総合対応案(まとめ)

個別の指摘を出し終えたら、最後に以下を含む総合対応案をまとめること:

1. **対応優先順位**: 全指摘をCritical→Highの順に並べ、着手すべき順序を提示する(依存関係がある場合は明記。例: 「Bを直す前にAの修正が前提」)。
2. **クイックウィン**: 修正コストが低く即座に対応できるものを別枠で列挙する。
3. **まとめて対応すべきもの**: 根本原因が共通していて一括修正できる指摘があれば、まとめて扱う提案をする(個別修正よりリファクタリングの方が適切な場合はその設計案を示す)。
4. **未解決のリスク**: コードの修正だけでは解決できず、運用・監視・ドキュメント側の対応が必要なものがあれば明記する(例: Amplifyの環境変数管理、AdSense/GA4などサードパーティ連携のCSP設定)。
